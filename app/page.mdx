# Your first Keploy tests in Go

<p className="mt-4! font-sans text-[1.0625rem] text-muted">A 20-minute walkthrough with a Gin + MongoDB URL shortener.</p>

You have a Go API. It talks to a database. You know you *should* have integration tests, but writing them means
spinning up Mongo in CI, seeding data, hand-writing request/response assertions, and keeping all of it in sync
with the code. So it doesn't happen.

This guide takes a different route. You'll use a small app the way a client would, with two `curl` calls, and
let **Keploy** turn that traffic into tests that run **without a database**. You won't write any test code.
Here's the whole idea in one session:

<SessionDemo />

<Callout type="info" title="Who this is for">
  You're comfortable with Go and the terminal, have used Docker before, and have **never touched Keploy**. You
  don't need to know Gin or MongoDB. We won't write any app code except one deliberate bug.
</Callout>

## How Keploy works (the 60-second version)

Keploy sits between your app and the outside world. It doesn't need an SDK or code changes because it hooks into
the network layer (using eBPF on Linux) and sees traffic going in and out of your process.

<RecordReplayDiagram />

- **In record mode**, every incoming HTTP request and the response your app sends back is saved as a **test case**.
  Every outgoing call your app makes while handling it (here: MongoDB queries) is saved, along with the reply, as a
  **mock**.
- **In test mode**, Keploy starts your app, fires the recorded requests at it, and compares the new responses to
  the recorded ones. When your app queries MongoDB, Keploy intercepts the query and answers from the mocks.

<Callout type="aha">
  That last point is the big one. Your tests are **integration tests** (real HTTP, real handlers, real driver code)
  but they're as **portable as unit tests**, because the database is replaced by recorded answers. CI doesn't need a
  Mongo container.
</Callout>

## Prerequisites

| Tool | Why you need it | Check |
| --- | --- | --- |
| Docker (Desktop or Engine) | Runs MongoDB, and the app itself in the Compose path | `docker --version` |
| Git | Clone the sample app | `git --version` |
| Go 1.22+ *(native path only)* | Run the app directly with `go run` | `go version` |
| Linux, macOS or Windows (WSL2) | Keploy's capture relies on Linux kernel features | `uname -a` |

<Callout type="warning" title="On Windows? Use WSL2">
  Keploy's network capture is built on Linux eBPF (kernel **5.10+**). On Windows, do everything in this guide
  inside a **WSL2 Ubuntu** shell, with Docker Desktop's WSL integration turned on. On macOS, Keploy's installer
  handles the setup for you. Check the [installation docs](https://keploy.io/docs/server/install/) for your platform.
</Callout>

## Step 2: Get the sample app

Keploy maintains a repo of sample apps. We'll use `gin-mongo`, a URL shortener with two endpoints:

- `POST /url` takes a long URL, stores it in Mongo, and returns a short link.
- `GET /:id` looks the ID up in Mongo and redirects (HTTP `303`) to the original URL.

```bash
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
```

<FileTree>
{`
gin-mongo/
├── main.go               # Gin router + Mongo connection
├── handler.go            # POST /url and GET /:id handlers
├── Dockerfile
├── docker-compose.yaml   # app (ginMongoApp) + mongo
└── keploy/               # tests already recorded by the Keploy team
    └── test-set-0/
`}
</FileTree>

<Callout type="tip" title="Start with a clean slate">
  The repo ships with a `keploy/` folder that already contains recorded tests. To make sure everything you see
  later was produced by *you*, delete it first: `rm -rf keploy`. (If you keep it, your recording simply becomes
  `test-set-1` next to it.)
</Callout>

## Step 3: Record test cases

Pick how you want to run the app. **Docker Compose** is the easiest path because nothing but Docker needs to be
installed. **Native** is closer to everyday development if you already have Go.

<Tabs labels={["Docker Compose", "Native (go run)"]}>
<Tab>

The Compose file attaches both containers to a network called `keploy-network` and marks it `external`, which
means Compose expects it to **already exist**. Create it once:

```bash
docker network create keploy-network
```

Now start the app *through* Keploy:

```bash
keploy record -c "docker compose up" --container-name "ginMongoApp"
```

- `-c` is the command Keploy should run to start your app.
- `--container-name` tells Keploy which of the Compose containers is *your app*, i.e. whose traffic to capture.
  It matches `container_name: ginMongoApp` in `docker-compose.yaml`.

</Tab>
<Tab>

Start only MongoDB in Docker:

```bash
docker compose up mongo
```

The app connects to a host named `mongoDb`, which only resolves inside the Docker network. Since the app now runs
on your machine, point it at `localhost` in `main.go`:

```go title="main.go" {1}
client, err := New("localhost:27017", dbName) // was "mongoDb:27017"
```

Then, in a second terminal, start the app through Keploy:

```bash
keploy record -c "go run main.go handler.go"
```

</Tab>
</Tabs>

<Callout type="warning" title="Permission denied?">
  On Linux, Keploy needs elevated privileges to attach its eBPF hooks. If `record` fails with a permission error,
  re-run it with `sudo -E env PATH=$PATH keploy record ...` so `sudo` can still find Go and Docker.
</Callout>

Wait until you see Gin's startup log (`Listening and serving HTTP on :8080`). The app is now running normally;
Keploy is just listening.

### Make some API calls

Open another terminal and use the app like a real client would. First, shorten a URL:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://google.com"}'
```

```json title="Response"
{"ts":1718943885198315028,"url":"http://localhost:8080/Lhr4BWAi"}
```

Then follow the short link:

```bash
curl --request GET --url http://localhost:8080/Lhr4BWAi
```

```html title="Response"
<a href="https://google.com">See Other</a>.
```

Each call shows up in the Keploy terminal as a captured test case. Stop recording with <kbd>Ctrl</kbd> + <kbd>C</kbd>.

<Callout type="aha" title="Why the short ID is always Lhr4BWAi">
  The app derives the ID from a SHA-256 hash of the long URL, so `https://google.com` *always* becomes `Lhr4BWAi`.
  That determinism is what lets the recorded `GET /Lhr4BWAi` keep passing on replay.
</Callout>

## Step 4: Look at what Keploy recorded

Keploy created a `keploy/` folder next to your code:

<FileTree>
{`
keploy/
└── test-set-0/
    ├── tests/
    │   ├── test-1.yaml   # POST /url
    │   └── test-2.yaml   # GET /Lhr4BWAi
    └── mocks.yaml        # every MongoDB call + its reply
`}
</FileTree>

Open `test-1.yaml`. Trimmed down, it looks like this:

```yaml title="keploy/test-set-0/tests/test-1.yaml" {13-16}
kind: Http
name: test-1
spec:
  req:
    method: POST
    url: http://localhost:8080/url
    header:
      Content-Type: application/json
    body: '{"url": "https://google.com"}'
  resp:
    status_code: 200
    body: '{"ts":1718943885198315028,"url":"http://localhost:8080/Lhr4BWAi"}'
  assertions:
    noise:
      body.ts: []
      header.Date: []
```

It's plain YAML: the exact request, the exact response, and an `assertions.noise` block.

<Callout type="aha" title="What is “noise”?">
  `ts` is a nanosecond timestamp, so it will be different on every run. If Keploy compared it strictly, the test
  would fail forever. Keploy noticed that the field (and the `Date` header) is non-deterministic and marked it as
  **noise**: it's ignored during comparison. If one of your own fields keeps changing (a UUID, a `createdAt`), add
  it to `noise` the same way.
</Callout>

`mocks.yaml` holds the MongoDB side: the `update` (upsert) issued by `POST /url` and the `find` issued by
`GET /:id`, each with the reply Mongo sent. These entries are what replace the database during testing.

<Callout type="tip">
  Commit the `keploy/` folder to Git. It *is* your test suite, and the YAML diffs are easy to review in PRs.
</Callout>

## Step 5: Replay the tests

Now let Keploy run the app again and replay everything it captured.

<Tabs labels={["Docker Compose", "Native (go run)"]}>
<Tab>

```bash
keploy test -c "docker compose up" --container-name "ginMongoApp" --delay 10
```

</Tab>
<Tab>

```bash
keploy test -c "go run main.go handler.go" --delay 10
```

</Tab>
</Tabs>

`--delay 10` gives the app 10 seconds to boot before Keploy starts sending requests. If your machine is slow and
the first test fails with a connection error, raise it.

Keploy prints each test's result followed by a summary for the test set. You should see **2 passed, 0 failed**.

<Callout type="aha" title="Try this: stop MongoDB">
  Run `docker stop mongoDB`, then run `keploy test` again (Native path). The tests **still pass**. The app's Mongo
  queries never reached a database; Keploy answered them from `mocks.yaml`. This is exactly what makes these tests
  cheap to run in CI.
</Callout>

## Step 6: Catch a regression

Passing tests are only useful if they fail when something breaks. Let's break something on purpose. In
`handler.go`, rename the `url` key in the `POST /url` response:

```go title="handler.go" {3}
c.JSON(http.StatusOK, gin.H{
	"ts":        time.Now().UnixNano(),
	"short_url": "http://localhost:8080/" + id, // was "url"
})
```

Run `keploy test` again.

<Callout type="warning" title="Compose users: rebuild the image">
  `docker compose up` reuses the image it built earlier, so it won't see your change. Use
  `-c "docker compose up --build"` for this run.
</Callout>

This time `test-1` **fails**, and Keploy shows a diff of the expected vs. actual body: `url` is missing and
`short_url` appeared. Any client that read `url` would have broken, and you found out without writing a single
assertion. Revert the change and the suite goes green again.

<Callout type="info" title="Intentional change?">
  If the new response is what you *want*, don't edit YAML by hand: delete the stale test (or the whole test set)
  and record again. Re-recording is the normal way to update Keploy tests.
</Callout>

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `network keploy-network declared as external, but could not be found` | Network not created yet | `docker network create keploy-network` |
| App can't reach Mongo when using `go run` | Host is still `mongoDb` | Change it to `localhost:27017` in `main.go` |
| First test fails with *connection refused* | App wasn't ready when replay started | Increase `--delay` |
| Code change has no effect in Compose mode | Old image reused | Add `--build` to the Compose command |
| Permission errors on Linux | eBPF needs root | Run Keploy with `sudo -E` |

## Recap and next steps

In about 20 minutes you:

1. **Recorded** real API traffic from a Go app, with no SDK and no code changes.
2. Got **YAML test cases and database mocks** you can read, review and commit.
3. **Replayed** them without MongoDB, and watched them **catch a breaking change**.

Where to go from here:

- Run `keploy test` in CI. See the [Keploy docs](https://keploy.io/docs/) for GitHub Actions setup.
- Try another Go sample (Echo + Postgres, Mux + MySQL) from [keploy/samples-go](https://github.com/keploy/samples-go).
- Point Keploy at your own service: record a few real flows and see what it catches.
